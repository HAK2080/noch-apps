# Noch loyalty: current-system map and feature decisions

## How to read this map

Scope is the loyalty program and the customer, POS, marketing, messaging, feedback and content features connected to it—not every finance, inventory or workforce feature in the wider ERP. Connections are traced from source and migration definitions at `b2ed42d`. Concurrent working-tree changes to POS instance locking and expense settings are outside this assessment; their changes were preserved. Source line positions may shift as that work continues. Historical documents help explain intent but do not override code.

**Potential (P), out of 5:** 1 = little relevance to the frictionless rebuild; 3 = useful supporting feature; 5 = essential customer/business value if implemented well. This is an analytical judgment, not forecast revenue.

**Outcome readiness (O), out of 5:** 0 = absent or retired from the current journey; 1 = isolated/legacy/unproven path; 2 = partial connection or material limitation; 3 = connected implementation with plausible functional outcome; 4 = freshly verified end-to-end in the intended environment; 5 = measured sustained business outcome. Current business outcomes are **unmeasured**, not zero. No feature receives 4 or 5 from source inspection alone.

**Keep** retains the useful capability and its safeguards. **Improve** fixes or connects it. **Toss** retires a redundant operating path, not its records, balances, earned rewards or audit evidence. All decisions are recommendations; nothing has been removed.

## Connection overview

```text
Customer checkout QR -> phone/email verification -> claim open POS session
                                              -> customer identity / membership
POS member scan or fallback lookup ------------> same customer identity
Paid POS order + line items --------------------> settlement rules
Refunds / voids --------------------------------> corrective settlement
                                                  |
                                                  +-> point events -> balance
                                                  +-> mission order events -> progress / bonus
                                                  +-> reward issuance -> earned reward
POS redemption --------------------------------> eligible discount + reward consumption
Capture decisions -----------------------------> linked / skipped / unknown audit
Owner controls --------------------------------> summaries / directory / missions / archive

Homepage loyalty + receipt passport ------------> OLD stamp/profile/reward readers
Public feedback -------------------------------> feedback / staff tasks
                                              -> OLD customer.points / loyalty_rewards
Marketing audiences + older challenges --------> OLD visits/stamps/rewards/challenge data
Campaigns + scheduled triggers -----------------> notification outbox -> consent check -> provider
Content Studio --------------------------------> AI drafts / publications / measurement
                                              [no verified closed-loop V2 offer decisioning]
```

Key finding: there is one new purchase-points engine, but several legacy customer and marketing paths around it. The public feedback writer is especially important because its reward output is not represented by the new purchase ledger in the inspected code.

## Highest-risk connection defects

1. **Customer value split:** new purchase ledger versus legacy feedback points/rewards. Reconcile by event/customer, not by summing both displayed balances.
2. **Experience split:** homepage overlay, static passport and the new checkout disagree about the program. Retain old URLs during transition.
3. **Unfinished new member destination:** a new self-service card RPC exists but has no current UI consumer.
4. **Two promotion engines:** new order-driven missions and old largely manual challenges.
5. **Automatic issuance versus choice:** current rule ordering will spend on cheaper active rewards before a member can save for more expensive ones.
6. **Misleading outcome signals:** rolling-window launch labels, possible sales multiplication in the member directory, legacy reward audiences and separate messaging logs.
7. **Incomplete transaction recovery evidence:** offline and delayed claims, refund-of-redemption, concurrent spend and ambiguous network responses need actual scenario testing.
